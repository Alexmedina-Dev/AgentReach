## 2. Detalle

### (a) Configuración de opencode en Windows

- **Global.** La página de solución de problemas da la ruta Windows exacta: "Windows : Press WIN+R and paste `%USERPROFILE%\.config\opencode\opencode.jsonc`" y para plugins `%USERPROFILE%\.config\opencode\plugins` (https://opencode.ai/docs/troubleshooting/). La página de config solo da `~/.config/opencode/opencode.json` y `~/.config/opencode/tui.json` (https://opencode.ai/docs/config/). No hay contradicción: el archivo puede ser `.json` o `.jsonc` (`names = ["opencode.json", "opencode.jsonc"]` en `packages/core/src/config/discovery.ts`).
- **Código.** `packages/util/src/global-roots.ts` calcula `config = process.env.XDG_CONFIG_HOME || path.join(os.homedir(), ".config")` más `opencode`, sin tratamiento especial de Windows. Es decir, en Windows no se usa `%APPDATA%`. Lo mismo para datos (`~/.local/share/opencode`), caché (`~/.cache/opencode`) y estado (`~/.local/state/opencode`). Consecuencia para AgentReach: si el entorno de opencode define `XDG_CONFIG_HOME`/`XDG_DATA_HOME`, las rutas cambian, igual que con `CLAUDE_CONFIG_DIR` en Claude Code. `OPENCODE_CONFIG_DIR` sustituye el directorio global en el código (`Effect.suspend(() => acquire({ config: process.env.OPENCODE_CONFIG_DIR ?? Path.config }))`), y la incidencia https://github.com/anomalyco/opencode/issues/32825 (abierta) dice que en v2 reemplaza la config global en vez de sumarse, lo que contradice la doc ("loaded after global").
- **Observación local.** En el PC de Alex existe `C:\Users\<usuario>\.config\opencode\` con `tui.json` y la carpeta `plugins` (no se leyó el contenido). No se afirma quién los creó: opencode no está en el `PATH` de este PC. Solo confirma que la ruta es coherente con lo anterior.
- **Gestionada.** Doc: `%ProgramData%\opencode` (https://opencode.ai/docs/config/). Código: `systemDirectory()` devuelve `path.join(env.ProgramData || "C:\\ProgramData", "opencode")` en `win32`. En el PC de Alex esa carpeta no existe (comprobado), lo esperable.
- **Cambios de v2 que importan al adaptador (código).** El descubrimiento de configuración incluye también carpetas `.claude` y `.agents` además de `.opencode` y los archivos `opencode.json(c)`, y recorre desde el directorio actual hacia arriba hasta la raíz git. Confirma que opencode 2.x puede leer `.claude/` (ya anotado en el documento original).

### (b) Herencia de variables de entorno

**Claude Code.**
- Tabla del sandbox: "Environment variables | Inherited from Claude Code, including any secrets in its environment" (https://code.claude.com/docs/en/sandboxing.md). Esa tabla describe lo que ve un comando; en Windows nativo no hay sandbox, así que el comando corre con el entorno heredado directamente. Es lectura literal más una inferencia corta, no una frase "Bash hereda todo" en la página de herramientas.
- Hooks: "A hook process inherits the parent environment, apart from the `OTEL_*` exporter variables that Claude Code removes from every subprocess it spawns and, when `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is set to 1, the variables it strips" (https://code.claude.com/docs/en/hooks.md).
- Excepción incondicional: las variables `OTEL_*` no llegan a Bash, hooks, MCP ni LSP (https://code.claude.com/docs/en/monitoring-usage.md).
- Servidores MCP stdio: heredan el entorno del shell salvo `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1` (https://code.claude.com/docs/en/env-vars.md).
- El bloque `env` de settings "reach every subprocess Claude Code starts" y son texto plano en el archivo (https://code.claude.com/docs/en/settings-reference.md). Los archivos de proyecto y local no pueden fijar `CLAUDE_CONFIG_DIR`, `HOME`, `TEMP`, `ComSpec`, `ProgramData`, etc.
- El scrub con `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` deja `GITHUB_TOKEN`, `GH_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `HTTP_PROXY`/`HTTPS_PROXY` (incluida la contraseña en la URL) y `GIT_CONFIG_*`, y deja "a secret whose variable name and value don't look like a credential" (https://code.claude.com/docs/en/env-vars.md). Es opt-in: sin la variable, no se limpia nada.

**opencode (código 2.x).** `packages/core/src/shell.ts`: `baseEnv = (entorno de la sesión) ?? process.env`, y el entorno del proceso hijo es `{...baseEnv, TERM: "xterm-256color", OPENCODE_TERMINAL: "1"}`; después se dispara el hook `shell create.before`, que puede modificar `invocation.env`. No hay limpieza de credenciales. Para MCP locales, la doc solo menciona `environment` (https://opencode.ai/docs/mcp-servers/); no se revisó el código de `packages/core/src/mcp/connection.ts` para la herencia de MCP: **eso sigue sin verificar**.

### (b3) Shell de opencode en Windows (relevante para parsear comandos y para S1)

`packages/core/src/shell/select.ts`: si hay `shell` en config o variable `SHELL`, se usa; si no, en Windows se elige el primero disponible de `pwsh`, `powershell`, Git Bash (`<git>\bin\bash.exe`), `COMSPEC`/`cmd.exe`. Argumentos: `-NoLogo -NoProfile -NonInteractive -Command` para PowerShell, `/c` para cmd, `-c` para el resto. La doc de config dice solo "pwsh or cmd.exe on Windows" (https://opencode.ai/docs/config/): es incompleta respecto al código. La incidencia https://github.com/anomalyco/opencode/issues/57359 confirma el uso real de `powershell.EXE` en Windows 11.

### (c) Esquema de las líneas del `.jsonl` de Claude Code

**Lo documentado.** Oficialmente solo hay cuatro cosas: ruta `~/.claude/projects/<proyecto>/<session-id>.jsonl`, donde `<proyecto>` es el directorio de trabajo con los caracteres no alfanuméricos sustituidos por `-` (y truncado a 200 caracteres con hash si es más largo) (https://code.claude.com/docs/en/sessions.md); cada línea es un objeto JSON con `type` ("Entries are JSON-safe objects, one per line"); las entradas deben tratarse "as opaque JSON-safe values" y se deduplican por `entry.uuid` (https://code.claude.com/docs/en/agent-sdk/session-storage.md); y `getSessionMessages()` devuelve `type` (`user`/`assistant`/`system`), `uuid`, `session_id`, `message`, `parent_tool_use_id` y `parent_agent_id` (https://code.claude.com/docs/en/agent-sdk/typescript.md). **No existe un esquema publicado de campos por tipo de línea.** Este es el punto que queda como "verificado empírico, sin contrato".

**Lo observado** (2.1.318/319, 6 archivos, 1.219 líneas; solo nombres de campos):

| `type` de la línea | Campos observados (resumen) |
|---|---|
| `user` | `parentUuid`, `isSidechain`, `uuid`, `timestamp`, `sessionId`, `cwd`, `version`, `gitBranch`, `entrypoint` (`cli`, `sdk-cli`, `sdk-ts`), `userType`, `promptId`, `message{role,content}`; en las líneas de resultado de herramienta además `toolUseResult`, `sourceToolAssistantUUID` y `permissionDecision{decision,source,reasonType}`; a veces `permissionMode` (`auto`, `bypassPermissions`, `dontAsk` en la muestra), `sandboxed`, `promptSource` |
| `assistant` | `parentUuid`, `uuid`, `timestamp`, `sessionId`, `requestId`, `message{model,id,role,content,stop_reason,usage,...}`, `effort`, `isSidechain` |
| `attachment`, `system` | `parentUuid`, `uuid`, `timestamp`, `sessionId`, `attachment` o `subtype` (`stop_hook_summary`, `turn_duration`, `away_summary` en la muestra) |
| Metadatos | `session-owner`, `queue-operation`, `last-prompt`, `ai-title`, `tools-used`, `mode`, `permission-mode`, `cost-state`, `file-history-snapshot`, `file-history-delta`, `api-request`, `api-request-blob`, `api-request-shape`, `atis-latch` |

- **Bloques de contenido** dentro de `message.content`: `text`, `thinking`, `tool_use{id,name,input}`, `tool_result{tool_use_id,content,is_error}`, `image`.
- **Enlace llamada-resultado.** Un bloque `tool_use` del asistente lleva `id`; el bloque `tool_result` del siguiente mensaje `user` lleva `tool_use_id` igual, y la línea `user` repite el `id` del asistente en `sourceToolAssistantUUID`. La cadena de conversación se reconstruye con `parentUuid`. Los subagentes viven en `<sesion>/subagents/` en el mismo formato (https://code.claude.com/docs/en/claude-directory.md).
- **Datos útiles para AgentReach fase 2 sin leer contenido.** Nombre de herramienta (`Bash`, `PowerShell`, `Read`, `Glob`, `Grep`, `Write`, `Edit`, `WebFetch`, `Agent`, `Skill`, `ToolSearch`), claves de `input` (`file_path`, `path`, `pattern`, `command`), la decisión de permiso (`decision`, `source`, `reasonType`: en la muestra `mode`, `classifier`, `other`), `cwd`, `timestamp`. El campo `toolUseResult` y los bloques `tool_result` contienen salida de herramientas, es decir, posibles secretos: un analizador debe descartarlos al leer.
- **Advertencia.** Las líneas `api-request`/`api-request-blob` repiten el prompt de sistema y la conversación; el campo `file-history-snapshot` apunta a copias de archivos. Todo esto cambia entre versiones (aparecieron tipos que la documentación no menciona); el analizador debe ignorar tipos y campos desconocidos y fijar la versión (`version`) en cada línea como dato de compatibilidad.
- **Limitación.** Muestra pequeña (6 archivos de este mismo PC). No se garantiza que haya otros tipos de línea.

### (d) Decisión de confianza del espacio de trabajo

- Documentado: se guarda "`projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`", donde `<path>` es la raíz del repositorio o la carpeta misma si no hay repositorio (https://code.claude.com/docs/en/permissions.md, sección "What runs before you trust a folder"; también https://code.claude.com/docs/en/mcp.md).
- Reglas de clave: en un repo, la raíz git (en un worktree, la del checkout principal); fuera de un repo, el directorio de arranque, y la confianza cubre subdirectorios salvo repos anidados; en el directorio personal (home) la confianza se guarda solo para la sesión y **no** se escribe a disco (https://code.claude.com/docs/en/security.md y permissions.md).
- Observado en el PC de Alex: `~/.claude.json` tiene una clave `projects` con 4 entradas, todas con `hasTrustDialogAccepted` (3 verdadero, 1 falso) y claves de ruta con `/` y letra de unidad, por ejemplo `C:/dev`. Es decir, en Windows la clave usa barras normales.
- Efectos legibles por AgentReach: antes de confiar, `permissions.allow` y `additionalDirectories` de `.claude/settings.json` del proyecto no se aplican; `deny` y `ask` sí; `-p` y el SDK nunca muestran el diálogo y siguen la columna "claude -p" de la tabla (hooks, `env` y `allowed-tools` de skills se usan; las reglas allow no; los servidores de `.mcp.json` se conectan sin preguntar).
- **Correcciones respecto al documento original.** (1) La tabla oficial dice que los hooks de settings y el bloque `env` del repositorio **sí se usan** en `-p` sin confianza; en sesión interactiva los hooks de todos los archivos se retienen hasta aceptar la confianza (https://code.claude.com/docs/en/hooks.md). (2) Un `.claude/settings.local.json` se trata como "del repositorio" (no confiable) si está versionado en git o si `.claude` es un enlace simbólico (permissions.md): AgentReach debe comprobarlo con `git ls-files`/estado de enlace antes de decir que sus reglas están activas.
- **Estabilidad.** `~/.claude.json` contiene también datos de cuenta y estado; la documentación la describe como estado de aplicación ("holds app state and UI toggles", https://code.claude.com/docs/en/debug-your-config.md), no como API. Que la clave `hasTrustDialogAccepted` esté documentada para escritura manual da una garantía parcial de estabilidad, pero AgentReach debe leer solo esa clave y descartar el resto del archivo.

### (e) Rutas Windows de skills y configuración gestionada de Claude Code

- **Settings y MCP gestionados (verificado).** `C:\Program Files\ClaudeCode\managed-settings.json`, `managed-settings.d\*.json` (fusión alfabética) y `managed-mcp.json`; registro `HKLM\SOFTWARE\Policies\ClaudeCode` valor `Settings`; `HKCU` solo si no hay documento de administrador por encima; "Claude Code doesn't read the legacy Windows path `C:\ProgramData\ClaudeCode\managed-settings.json`" (https://code.claude.com/docs/en/managed-settings.md). Se admite que el archivo sea un enlace simbólico; si apunta fuera del directorio se emite aviso en `/status` y `claude doctor`. Orden de fuentes y `first-wins` como ya se tenía (servidor, MDM/HKLM, archivos, HKCU).

### (f) opencode: reglas `deny` y shell

**Lo que muestra el código 2.x.** La herramienta shell (`packages/core/src/tool/plugin/shell.ts`) hace dos comprobaciones antes de lanzar el proceso: `access.authorizeExternal` sobre el directorio de trabajo y los directorios que su analizador deduce, y `permission.assert({action: "shell", resources: <comandos analizados>})`. No hay ninguna evaluación de reglas `read` ni `edit` sobre los archivos que el comando abre. Por tanto, un `read: deny` o `edit: deny` **no** frena `cat`, `grep -r`, `python -c` etc.; solo lo hace una regla `shell`. (El `deny` de `read` se aplica a la herramienta `read`.)

**Lo que dice el proyecto.**
- https://github.com/anomalyco/opencode/issues/56545 (cerrado "not planned", 2026-10-18): el bot oficial del repositorio (`opencode-agent[bot]`, con asociación CONTRIBUTOR; no es un mantenedor humano) responde que las reglas de shell "match the command text the scanner produces, not the files a command ends up reading. A filename deny like `*.env*` was never a sandbox for the shell tool", y recomienda una lista de permitidos estrecha o ejecutar en contenedor/sandbox. Reconoce que la documentación debería decirlo con más claridad.
- https://github.com/anomalyco/opencode/issues/56288 (abierta): con `external_directory: ask` el escritor de archivos pregunta pero `shell` no; reproducido por el bot en 2.0.32 y en `dev` (Linux). El reporte original usa rutas de Windows y PowerShell. La documentación afirma que `external_directory` aplica a "many bash commands" (https://opencode.ai/docs/permissions/); la conducta observada contradice eso para escrituras por shell. **Estado: contradictorio entre doc y conducta.**
- https://github.com/anomalyco/opencode/issues/42979 y 54465 (v1): cerrados por inactividad y por la migración a 2.0 respectivamente; no refutan nada, simplemente no se reabrieron. Un miembro del proyecto (`thdxr`) cerró el 54465 pidiendo reabrir si persiste en 2.0; 56288 es esa persistencia.
- https://github.com/anomalyco/opencode/issues/58775 (abierta, reproducida): un `deny` de shell solo coincide con el texto crudo; `sh -c` se deniega, pero `/bin/sh -c`, `env sh -c`, `command sh -c`, `FOO=1 /bin/sh -c` pasan. Las reglas de rutas absolutas pueden quedar inertes frente a rutas relativas.
- https://github.com/anomalyco/opencode/issues/54393 (cerrado como completado): en Windows con PowerShell, un `--` suelto hacía que el analizador no devolviera comandos y se saltara la comprobación. Hay un duplicado abierto sobre redirecciones sin comando (`>` solo), mencionado en 57359 como issue 49948; no se leyó.
- https://github.com/anomalyco/opencode/issues/56470 (abierta): reporte de que `ask` no detiene el comando; el bot **no** lo reprodujo. Estado: no confirmado, no usar como hecho.
- La cita `[TERCERO]` de Intility queda corroborada en lo esencial por el código y por el propio proyecto, pero ahora hay fuente primaria; ya no hace falta citar a Intility.

**Consecuencia.** Para opencode 2.x, "deny de lectura/edición" no es barrera sobre el shell; el único control de comando es `shell` por texto, evadible por ortografía (58775). La capacidad declarada `AUDITAR_Y_ADVERTIR` sin bloqueo queda reforzada.

### (g) Hooks, env-vars, mcp, sandboxing, skills, security, permission-modes

Hechos nuevos o corregidos (todos en https://code.claude.com/docs/en/):

- **hooks.md.** `PreToolUse` devuelve `allow`, `deny`, `ask` o `defer` y precedencia `deny > defer > ask > allow` entre hooks; `allow` no salta reglas `deny`/`ask` ni acciones que ningún modo auto-aprueba. Un hook que sale con código distinto de 0 o 2 es "non-blocking error": la acción sigue, salvo `onFailure: "block"` (requiere v2.1.295 o posterior). En Windows sin Git Bash, un hook `PreToolUse`/`PermissionRequest` en forma shell que falla con `onFailure` sin fijar puede **bloquear** la llamada. Un hook que expira no bloquea por defecto. Los hooks de settings, política y plugins se ejecutan también dentro de subagentes; el matcher `mcp__.*` cubre herramientas MCP (los de plugin usan `mcp__plugin_<plugin>_<servidor>__<herramienta>`). `transcript_path` se escribe de forma asíncrona.
- **permissions.md.** Reglas `deny` en todos los modos, incluido `bypassPermissions`. Los comandos Bash de solo lectura (`ls`, `cat`, `grep`, `find`, `head`, `tail`, `wc`, `diff`, `stat`, `du`...) "run without a permission prompt in every mode", salvo lo que cambie `permissions.blockReadsOutsideWorkingDirectories`. Redirecciones de entrada (`< archivo`) y `tee` tienen comprobaciones propias. Las rutas UNC en Windows piden permiso y no se aceptan como directorio de trabajo.
- **permission-modes.md.** El modo por defecto integrado puede ser `auto`: desde v2.1.233 en Windows nativo (antes era Manual). Un `defaultMode` `auto` o `bypassPermissions` en `.claude/settings.json` o `.claude/settings.local.json` no surte efecto. "Protected paths" (`.git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.config/git`, y los propios `.claude/`) nunca se aprueban solos salvo en `bypassPermissions`. En el PC de Alex las transcripciones muestran `auto`, `bypassPermissions` y `dontAsk`.
- **sandboxing.md.** Confirmado dos veces: "On native Windows, Claude Code runs commands unsandboxed" y con `failIfUnavailable` Claude Code sale al inicio en Windows nativo. Herramientas que corren fuera del sandbox incluso donde existe: Read/Edit/Write/WebFetch/WebSearch, hooks de comando, servidores MCP locales, comandos auxiliares (`statusLine`, `apiKeyHelper`).
- **security.md.** Las credenciales en Windows se guardan "in a file that inherits the access controls of your user profile directory". Mitigaciones: `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1`, `cleanupPeriodDays` (por defecto 30, mínimo 1), `claude purge`.
- **mcp.md.** Confirmado el comportamiento de `.mcp.json` ante `claude -p` sin confianza: se conecta sin preguntar. `enableAllProjectMcpServers` en el archivo del proyecto no cuenta si el repositorio no es de confianza.
- **skills.md.** `allowed-tools` de un skill de proyecto se aplica incluso en `-p` en carpeta no confiable; `allowManagedPermissionRulesOnly` lo ignora.
- **env-vars.md y settings-reference.md.** Ya cubiertos en (b). Nuevo: `CLAUDE_CODE_PROJECT_DIR_NAME` permite cambiar el nombre de la carpeta de proyecto en `projects/`, de modo que AgentReach no debe derivar la ruta solo de la regla de sustitución por `-`; debe aceptar un directorio de transcripciones arbitrario.
- **Sin releer completos** (siguen con la salvedad de la sección 0): partes de `monitoring-usage` (solo se revisó configuración de administrador, `OTEL_*` y `TRACEPARENT`), `settings-reference` (se leyeron las entradas de confianza, `env`, sandbox y gestionados) y `mcp` (alcances y aprobación). No se encontraron contradicciones con el documento original en lo revisado.

### S5. `os.access` en Windows

En el código de CPython 3.13 (`Modules/posixmodule.c`, función `os_access_impl`), la rama de Windows llama solo a `GetFileAttributesW` y devuelve verdadero si el archivo existe y (no se pidió escritura, o el archivo no es de solo lectura, o es directorio). Comentario del propio código: "Access is possible if we didn't get a -1, and write access wasn't requested, or the file isn't read-only, or it's a directory". No se consulta el descriptor de seguridad ni la ACL. La documentación de Python (https://docs.python.org/3/library/os.html) dice que usar `access()` antes de abrir crea una condición de carrera, que el resultado puede diferir de las operaciones reales ("I/O operations may fail even when access() indicates that they would succeed") y que en Windows `chmod` solo gobierna el atributo de solo lectura. Conclusión: S5 queda **verificado** y la opción B de AD-5 se descarta con fuente. Además, la documentación aconseja la técnica EAFP (intentar y capturar `PermissionError`), pero el diseño de AgentReach no puede abrir el archivo, así que la alternativa para "legible por el SO" en Windows debe ser consultar la ACL (por ejemplo con la API de seguridad de Windows) o aceptar un resultado "no determinado". Esa alternativa no se evaluó aquí.

### S6. Junctions sin administrador

- Microsoft documenta que `mklink /j` crea una unión de directorio (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/mklink) y que el derecho de crear symlinks (`SeCreateSymbolicLinkPrivilege`) lo tienen por defecto los Administradores (https://learn.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/create-symbolic-links). `CreateSymbolicLink` admite `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` solo con modo de desarrollador activo (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinka); Python lo repite ("unelevated symlinks on Windows with Developer Mode", versión 3.8). **Ninguna de esas páginas dice que las junctions estén exentas del privilegio.** La página de enlaces duros y junctions (https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions) describe qué se puede enlazar, pero no los requisitos de privilegio.
- Fuentes de terceros que sí lo afirman (no valen como cierre): el wiki de Git for Windows (https://github.com/git-for-windows/git/wiki/symbolic-links) dice que los usuarios sin privilegios pueden crear junctions por defecto.
- El código de pruebas de CPython (`Lib/test/test_os/test_os.py`) crea junctions con `_winapi.CreateJunction` y solo salta la prueba si falla, lo que es coherente pero no concluyente.
- **No se ejecutó prueba** (la regla de no modificar el sistema lo impide). Cierre recomendado: una prueba de dos líneas en directorio temporal, en el PC de Alex y en el runner de CI. El supuesto se mantiene con "marcar como prueba condicionada al entorno" (el borrador ya lo prevé).
